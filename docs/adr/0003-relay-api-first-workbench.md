# ADR 0003 — Relay API-first teaching workbench

Date: 19 October 2026. Status: accepted for local implementation following the owner's expanded teaching authorization. Supersedes the previous product choice; historical artifacts remain available in Git tags.

## Decision

Use a fictional logistics support-resolution workflow with FastAPI and a same-origin buildless frontend. Prepare ordinary API mechanics before class; isolate later demonstrations as opt-in modules/profiles with separate runtime databases. Preserve the original four-contact timing, meaningful live changes, zero-key fallback and honest evidence requirements.

## Rationale

Cases, policy evidence, read tools and supervisor-approved credits make AI trust boundaries and business outcomes easy to inspect. Durable approval/freshness workflows justify Temporal and scheduling; ticket delivery justifies MCP and Codex; reviewed ingestion justifies skills and governance. The UI avoids unrelated navigation/game rules. The backend and frontend remain separate modules behind explicit OpenAPI contracts without requiring another development server or auth proxy.

## Consequences

The root app commands run Relay. Legacy aliases and dependencies were removed on 20 October 2026; historical tags preserve the earlier implementation. The local identity adapter is deliberately restricted to loopback and fails production startup. Reference SDKs are optional and never imported by baseline startup. Local fixture/SDK/Temporal results do not prove live model quality, hosted integration success, production security or independent participant proficiency. Actual provider/customer preflight, advanced practice and timed rehearsal remain separate delivery gates.
