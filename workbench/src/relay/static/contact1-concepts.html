Let me give you the situation. Kora Dispatch is a Nigerian logistics company whose support team is overwhelmed with customer questions. A customer paid ₦8,000 for express delivery, but the parcel arrived two days late and they want compensation.

Relay is the support agent’s application. The agent uses its AI assistant to check the shipment and company policy, then prepare an answer for the customer. We’ll use that situation to understand the parts of a grounded AI application.

Think of the model as the horse. It brings the capability. The harness is the software around it that coordinates the work: what information goes in, which tools can run, how their results come back, and when to stop.

In Relay, that includes the tool loop, conversation context and output checks. A more capable model still needs those pieces around it.

You’ll also hear me say ‘evaluation harness’. That’s a separate meaning: the code that runs our test questions and checks the results.

Speaker notes

Governance answers questions like: who may use this information, who can approve an action, and who is responsible when something goes wrong?

We can think of rules and enforcement, like laws and the police. Kora’s rule is that a supervisor must approve compensation. Our system has to enforce that rule, even if the model tries to skip it.

Our backend runs the AI through a harness: code that manages model calls, tools, context and stopping rules. The backend also enforces permissions and supervisor approval. These controls work together in the same application. People still own the policy, review the risks and remain accountable for the system.

Speaker notes

The Responses API is how we ask the model to do work. We send instructions and input. The result can contain text or a request to call one of the tools we supplied.

responses.create makes a model request and returns its output items. responses.parse also makes a model request, but adds our output schema and parses the answer into a Python object. We don’t pass the result of create into parse just to reformat it.

For a tool-assisted answer, one request can ask for shipment information. Our backend validates and executes that tool request, then a later request includes the result and asks for the final structured answer. We still validate completion, refusals and citations. Matching a schema doesn’t prove the answer is correct.

Speaker notes

Qdrant is the vector database we’re using here. It stores the embeddings and searches for similar passages. We chose its local mode so this workshop needs no separate database service or hosted database key. Other options include PostgreSQL with pgvector, Pinecone, Weaviate and Milvus. The right choice depends on the application’s existing database, filtering needs, scale and operating requirements.

The model doesn’t automatically know Kora’s current policies. We need to find the relevant policy and include it with the question. That’s what we’re using RAG for.

There are two paths here. Before answering questions, we split the approved documents into smaller passages, create embeddings and store them in Qdrant. An embedding is a list of numbers that helps us compare meaning.

When a question comes in, we embed the question too, search for similar passages, and send the useful evidence to the model. The local Qdrant store needs no service key; the embedding calls use our configured provider account.

Permissions apply before we choose the results. We also check that each passage still matches the current approved document. If a policy changes or is withdrawn, an old vector or saved conversation must not keep bringing it back into the answer.

Vector-store references: Qdrant · pgvector · Pinecone · Weaviate · Milvus.

07 / Grounding and abstention

“Why was the driver late?”

Explains credit eligibility.
Doesn’t establish the cause.

When the evidence runs out, abstain and escalate.

Code · click to copy

Speaker notes

Finding a related policy is only the first step. We still need to ask whether it actually supports the answer.

Suppose the customer asks why the driver was late. Our delivery policy can explain what compensation may be available. It doesn’t tell us why that particular driver was delayed. The model needs shipment evidence for that, or it needs to say the cause is unknown.

That’s why I’ll check both the retrieved passage and the claim in the answer. A citation can point to a real document while the sentence beside it says something the document never supported.

Our similarity threshold is a starting value, not a guarantee. An unrelated question might still retrieve a passage. We need to test whether the model recognizes when that evidence is insufficient.

08 / Tools, workflows and agents

Function calling: request → validate → execute.

  1. 01SelectFunction name + JSON arguments
  2. 02ValidateSchema, allowlist, case scope
  3. 03ExecuteAuthorized read; return call_id
  4. 04ContinueAppend output → next response

Workflow: fixed read, then answer. Agent: bounded turns, tools and deadline.

Code · click to copy

Speaker notes

The model needs shipment facts, so we give it a tool called get_shipment. It can request that tool by returning a name and arguments. Our application checks the request, reads the permitted shipment and sends the result back with the matching call ID.

The model doesn’t get access to every shipment just because it asks for an ID. We check the case, the tool’s arguments and the remaining request budget before executing it. The policy-reading tool can only read passages already allowed for this run.

We have two execution modes. The fixed workflow reads the shipment and produces an answer. The agent mode allows a few more tool-and-model turns, with a hard stopping limit. Both expose read-only tools. Neither gives the model a way to approve compensation.

We preserve the response items needed to continue the tool loop. That doesn’t mean exposing private model reasoning in the interface or logs. This reference executes tool reads sequentially; parallel tool execution is a separate design choice.

Speaker notes

When the agent asks a follow-up question, the model needs the relevant earlier context. Saving that exchange in our database doesn’t automatically include it in the next request.

With caller-managed history, our backend chooses earlier messages and sends them with the new question. Relay defaults to no history. When case context is enabled, it selects up to three supported exchanges within 6,000 characters and rechecks permissions and policy versions.

Native OpenAI offers two other approaches. previous_response_id links the next request to a prior response; we send current instructions again. The Conversations API keeps a persistent conversation whose ID we attach to Responses calls. Responses generates the output; Conversations stores the history. Our OpenRouter route supports the caller-managed approach.

Our backend runs the AI through a harness that manages its model calls, tools, context and stopping rules. The same backend also checks permissions, compensation eligibility and supervisor approval. The model’s output cannot replace those checks.

We need to assess both the answer and the actions taken. An answer might make an unsupported promise even when the backend correctly blocks the action.

11 / OpenAI streaming → FastAPI SSE

Streaming: events before the final answer.

  1. response.createdThe provider starts a response.
  2. response.output_text.deltaText arrives incrementally.
  3. response.completedInspect the final response and usage.

Relay streams progress, then a validated answer. Failure or cancellation must not save partial claims.

Code · click to copy

Speaker notes

Streaming lets us receive events while the model is producing its answer. That can make the application feel more responsive, but partial output hasn’t passed our checks yet.

Relay consumes the provider’s stream and shows progress while it waits for the complete structured answer. The backend then checks the result before displaying or saving it. The browser’s progress events are application events; they aren’t the same as the provider’s raw events.

Cancellation stops later steps and prevents partial-answer persistence. A network request already in progress may still take time to finish or time out.

Speaker notes

A trace shows the steps in one investigation: retrieval, embeddings, tool calls, generation and validation. We use Langfuse to follow those steps and see where time or failures occurred.

The run ID links those observations together. Prompt, model and policy versions help us identify what was used. Timing and token counts let us investigate latency and usage.

We export selected metadata rather than raw questions, policy passages, answers or private model reasoning. Access and retention rules still matter. Seeing a local trace and confirming receipt in a hosted collector are separate checks.

Speaker notes

How do we know this works beyond the one question we just tried? We need a repeatable set of questions with expected results.

I’ll separate three checks. Did retrieval find the right information? Does the answer make claims that the evidence supports? Did execution respect the tool and approval rules?

Our examples include paraphrases, restricted information, missing evidence and attempts to bypass the rules. They’re synthetic workshop cases, so the expected answers still need domain review.

A model can help grade an answer, but its verdict also needs checking against human reviews. Even a perfect source-ID score doesn’t tell us that every sentence is correct or that the application is ready for customers.

Speaker notes

To compare models fairly, keep the questions, policies and grading rules the same. Then compare supported answers, failures, latency and token usage. The 1,800-token output budget limits generation per request; reasoning and verbosity settings depend on what the selected model supports.

p95 latency means 95% of the measured runs finished within that time. Cached-input tokens tell us how much input the provider served from cache. A dated price card lets us estimate token cost, but an estimate is not an invoice.

These tools have different jobs. FastAPI handles requests and application rules. In this project, LangChain can split documents into chunks. LangGraph organizes execution steps and branches. Temporal handles workflows that need to survive waits, retries and restarts; it belongs to the later contact.

A new framework or configuration setting is a choice to test. It only counts as an improvement when the results show it helped.
