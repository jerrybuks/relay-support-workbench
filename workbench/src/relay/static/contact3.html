BE: src/utils/evaluation.py:16,112,120,140 · src/querying/agents/orchestrator.py:352

Speaker notes

Our LLM judge scores relevance, accuracy, completeness, clarity and helpfulness. It receives the query, agent names and the first 2,000 response characters, then submits scores and reasoning to Langfuse. It does not receive source facts, a reference answer or database outcomes, so I won’t treat its accuracy score as proof. It runs in the background when a trace ID exists, and missing fields can default to 5. We would need better grounding, score validation and human calibration before using it as a quality gate. We won’t invent scores or make paid judge calls in this demo.

Appendix · Reference

Three limits to discuss before production.

Identity & state

IP-derived sessions can share state.
Memory and cart are process-local.

Evaluation

Routing pass ≠ correct answer.
Judge lacks reference evidence.

Reliability

Background judge is not durable.
Transaction ≠ complete idempotency.

Useful engineering patterns can coexist with unfinished production requirements.

BE: src/routes/user.py:54,134 · src/utils/memory.py:17 · src/utils/cart.py:28 · src/querying/tools/order.py:704

Speaker notes

Before we call this production ready, we need to address identity, evaluation and reliability. Shared IP sessions can share shopping state, and incognito browser contexts do not fix that server-side identity choice. Process-local carts and memory can reset or diverge across workers. A routing pass is not an answer-quality pass, and a background task is not a durable workflow. We’ll keep these limitations visible without turning today’s small task into a redesign.

MCP connection / reference

Who connects to our MCP server?

Browser Inspector UI → local HTTP → Inspector’s Node.js backend
Inspector backend → MCP over stdio → our Python MCP server
Python tool → fixed golden JSON → results return along the same path

The toggle starts the client connection. No model is involved in this test.

Our server
MCPServer(...) → register tool → mcp.run(transport="stdio")

Codex later
Configure the same launcher in Codex. The host makes the tool available to its model.

server.py:15,23,34 · Inspector is the existing @modelcontextprotocol/inspector package.

Speaker notes

I built the Python server, not the Inspector interface. Inspector is an existing npm package. When I switch its toggle on, the browser asks Inspector’s local backend to connect. The backend already has our Python command and server-file path. It launches that file, which reaches mcp.run and waits for MCP messages on stdin. Inspector initializes the connection, lists tools and sends calls over the child process’s input/output streams. It displays the returned results in the browser. The SDK creates the schema from our function signature and docstring and handles protocol messages and argument validation. No model was connected in this test. Codex is a separate possible client: its host would need the same launcher configured before its model could use this tool. Our Python stdio server has no web URL of its own.
